Problem Statement and Context

Background

First-pass screening is slow and uneven

Recruiters read a resume against a job description and assign an informal fit. The same pair can be labelled differently by two reviewers, and obvious mismatches still consume the same reading time as close calls.

Current status

Keyword filters miss real signal

Applicant systems match strings. They miss synonyms, career switchers, and keyword-stuffed resumes, and they leave name, contact, and demographic text in the file the reviewer sees.

Why this topic

Triage, with a person still deciding

The useful agent is a consistent first label — Strong Match, Possible Fit, or Not Relevant — with evidence, a confidence score, and a stop for human review. It is a screening aid, and a recruiter decides who moves forward.

Design thinking

From recruiter pain to a bounded agent

Empathize

Time is lost on clear mismatches, and names leak into judgment.

Define

Produce an evidence-backed label without PII, and pause when unsure.

Ideate

Parse and score as separate agents, with retrieval and fixed label rules.

Prototype

Streamlit Screen, Review, and Log on one LangGraph run.

Test

30 balanced pairs, with accuracy, false-positive, latency, and audit gates.

Project Objectives

1

Build a grounded scorecard

Ingest a resume PDF and a job description, parse them into typed profiles, retrieve same-family competency benchmarks, and score skills, experience, and education with quotes found in the resume.

2

Route with a human checkpoint

Auto-persist high-confidence Strong Match and Not Relevant. Pause Possible Fit and any case under 0.7 confidence so a recruiter can keep, upgrade, or downgrade the label.

3

Keep PII out and audit every run

Drop name, email, phone, gender, age, nationality, photo, and address before scoring. Write a SQLite tracking row for every run, including failures, and append recruiter decisions to an override log.

4

Prove the loop on a fixed eval set

Score 30 labelled pairs and clear the gates: accuracy at least 85%, false-positive rate at most 5%, p95 latency under 90 seconds, and an audit row for every case.

Current Vs Proposed Approach

Current manual screening

1Recruiter opens a PDF and a job description side by side.
2They scan for keywords, years, and degree, with the candidate’s name and contact still visible.
3Fit is a private judgment. Synonyms and career changes are easy to miss, and stuffed keyword lists are easy to reward.
4Notes live in email or a spreadsheet. A second reviewer cannot see why the first label was chosen.
5Close calls and clear mismatches take the same kind of reading time.

Proposed agentic workflow

1Screen page accepts a resume PDF and a JD, or a demo fixture.
2PyMuPDF extracts text. The parsing agent returns profiles and drops PII. The UI never shows a name.
3Chroma returns competency chunks for that role family. The scoring agent rates three dimensions and grounds evidence in the resume.
4Fixed rules set Strong Match, Possible Fit, or Not Relevant. Missing must-haves cannot become Strong Match.
5High-confidence clear labels persist. Uncertain cases interrupt for Review. Every path writes an audit row.

System Architecture

Workflow: Resume Screening and Triage Agent — LangGraph ingest → parse → retrieve → score → validate → persist or HITL

1

TRIGGER

A recruiter starts a run from Streamlit: upload a resume PDF and paste or upload a JD, or click a demo fixture. start_screening opens a checkpointed thread.

2

SENSE

PyMuPDF reads the PDF. The JD is plain text. Retrieval pulls the top competency chunks for the parsed role family from the Chroma collection competency_benchmarks.

3

REASON

The parsing model emits a CandidateProfile and a RoleProfile. The scoring model rates skills, then experience, then education. Label rules, coverage, and confidence are applied in code.

4

ACT

The retriever is a LangChain tool. Structured output is validated with Pydantic. The graph inserts a tracking row, or interrupts and waits for resume_review.

5

OBSERVE

Strong Match or Not Relevant at confidence ≥ 0.7 auto-persists. Possible Fit or lower confidence stops for a person. Scores of 8 or more need resume-grounded evidence. Errors are still audited.

Agentic Workflow

Sense

Resume PDF, job description, and 40 O*NET-inspired competency notes. Role families: engineering, product design, operations. Untrusted text is wrapped in resume and job-description delimiters before the model sees it.

Reason and plan

Two LLM steps with a fixed graph plan: parse, then retrieve, then score. The model proposes dimension scores and evidence. Code decides the label, so a missing must-have cannot be talked into Strong Match.

Act

Tool call into Chroma (top 5, same family). One retry if parsing fails validation. Persist the scorecard, or pause the thread. Recommended action is advance, hold, or reject.

Observe and reflect

Evidence quotes must appear in the resume text; thin evidence lowers confidence and adds recruiter questions. The Review page resumes the same thread after a browser refresh.

Implementation and Demo

Page 1

Screen

Upload a PDF and a JD. The page shows dimension scores, overall label, confidence, rationale, benchmark titles, and a recommended action. A Possible Fit or low-confidence result shows a review banner. The candidate name is omitted.

Page 2

Review

Pending HITL rows list the agent’s questions. The recruiter keeps, upgrades, or downgrades the label, adds notes, and submits. SQLite checkpoints keep the in-flight review across a refresh.

Page 3

Log

Audit table with filters for label, role family, and overridden rows, plus CSV export. Filename is allowed. Demographic columns are absent.

Analysis and Results

86.7%Accuracy on 30 synthetic pairs. Gate was 85%.
0%False positives: no Not Relevant case labelled Strong Match.
7.6sp95 latency. Gate was under 90 seconds.
100%Audit completeness. Every harness case has a tracking row.

What the numbers say

The label is stable enough to triage a balanced synthetic set, and it does not promote clear mismatches to Strong Match. Recruiter time shifts to Possible Fit and low-confidence rows.

Why the label holds

Strong Match requires skills ≥ 8, experience ≥ 7, education met, and must-have coverage of at least half. Quotes that are absent from the resume are dropped, and a score of 8 or more without evidence is lowered.

What to treat carefully

These figures are from the 30-pair synthetic set, not live applicants. The optional open-resume import uses weak overlap labels. Quote that set only after a person reviews the labels.

Suggestions and Conclusions

Insights

A bounded agent is the product

  • Separate parsing from scoring, and keep the final label in deterministic rules.
  • Stop the graph when the case is ambiguous, and show the questions the model could not answer.
  • Treat the scorecard as a triage aid. A person decides who advances.
Next step

Close the packaging gap

  • Run the Docker Compose smoke on a machine with Docker. The image already serves Streamlit on 8501 and ingests Chroma if the index is empty.
  • Re-run the harness after any prompt or model change, and keep the four gates as the release check.
  • Review open-set labels before using them in a reported accuracy.
Future scope

Calibrate, then connect

  • Use recruiter overrides as a calibration set for prompts and the confidence threshold.
  • Batch several resumes against one JD inside the same audit model.
  • ATS handoff, login, and interview decisions stay out of scope for this capstone.
